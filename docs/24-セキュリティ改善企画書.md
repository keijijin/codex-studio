## 1. エグゼクティブサマリー

2026-11 の外部セキュリティレビューおよび再レビューにおいて、ワークスペース外への書き込み抜け道と、ユニットテストでは検出できない起動不能（preload / ESM `require`）が繰り返し発生した。個別パッチでは同種の欠陥が再発するため、**ファイル操作の単一入口化・プレビュー/実行の型分離・実アプリ検証の CI 必須化**を中核とする改善イニシアチブを立ち上げる。

本企画の目的は、一般配布前に「同じ抜け道を構造的に書けない」「起動経路の回帰を自動検出する」状態を確立することである。

---

## 2. 背景と課題

### 2.1 背景

- MVP α 向けの P0 改修（XSS、IPC、preview 実行、信頼、realpath）は一部完了した
- 再レビュー・再々レビューで、修正の副作用として起動不能や新たな symlink 脱出が検出された
- 現状の防御は「各ツールが正しく `resolveWithinWorkspace` を呼ぶ」ことに依存しており、呼び出し忘れが致命傷になる

### 2.2 解決したい課題

| 課題 | 現状 | 目指す姿 |
|------|------|----------|
| ファイル書き込みの抜け道 | MemoryAppend / BOARD.md 等が `fs` を直接利用 | すべて `WorkspaceFs` 経由。直接 `fs` は ESLint で禁止 |
| 起動不能の見逃し | ユニットテスト緑でも実アプリが起動不能 | E2E が `workspace:open`・preload・パッケージ起動を検証 |
| 承認前実行 | `executeMode` と `requiresApproval` の組み合わせ漏れ | `preview()` / `apply()` 分離と `ask` 一本化 |
| 信頼境界の静的さ | パス単位の一度きり信頼。`untrust` UI なし | 設定ハッシュ再確認 + 信頼解除 UI |
| 情報持ち出し | 未信頼でも Read + WebSearch が承認不要になり得る | 未信頼時 network を ask、秘密ファイルは Read 制限 |
| 配布前作業の残存 | Electron 更新、署名、audit、パッケージ未検証 | 配布ゲートとして明示し完了条件を定義 |

### 2.3 レビューで確認済みの再発パターン

1. **パス検証の迂回** — ツールが `ctx.resolvePath` を通さない
2. **サンドボックスとビルド形式の不整合** — ESM preload + `sandbox: true`
3. **ESM 実行時とテスト環境の差** — `require` がユニットでは潜在、実機で表面化
4. **承認条件の論理積漏れ** — `ask && requiresApproval` により Team 等が無承認実行

---

## 3. 目的

1. **構造的安全性**：同じクラスの欠陥をコンパイル時 / lint 時 / CI 時に阻止する
2. **検知可能性**：実起動経路・信頼ダイアログ・パッケージ版を自動検証する
3. **運用可能な信頼モデル**：信頼の付与・再確認・取り消しがユーザー操作として完結する
4. **配布準備**：署名・Electron 追従・パッケージ起動確認を改善計画に組み込む

---

## 4. スコープ

### 4.1 本イニシアチブに含める（Phase S1〜S4）

| Phase | 名称 | 概要 |
|-------|------|------|
| S0 | 配布ゲート | Electron 更新方針、署名、パッケージ起動、audit 方針 |
| S1 | 検出ゲート | 実アプリ E2E、PoC の `tests/security` 化 |
| S2 | 構造ゲート | `WorkspaceFs`、ESLint 禁止、`preview`/`apply` 分離 |
| S3 | 境界ゲート | 持ち出し対策、信頼ハッシュ、env allowlist、preload チャンネル制限 |
| S4 | 体験・保守 | 巻き戻し UI、セッション許可、監査/コスト UI、巨大ファイル分割 |

### 4.2 本イニシアチブに含めない（別ゲート）

- OS 級 Shell 隔離（`sandbox-exec` / bubblewrap / コンテナ）— 一般公開段階で再開
- Cloud / Remote Agent 実行
- マルチルート相対パスの完全 UX（S2 の `WorkspaceFs` 設計にはマルチルート対応を含めるが、UI 刷新は別枠）

### 4.3 完了の定義（DoD）

次をすべて満たしたとき、本イニシアチブの「配布可能判定」をレビュー可能とする。

1. `WorkspaceFs` 以外のツール内 `fs` 直接書き込みが ESLint で失敗する
2. `tests/security` が CI 必須で緑、かつレビュー PoC の主要シナリオをカバーする
3. CI 上でパッケージまたは同等ビルドの起動 + `workspace:open` E2E が緑
4. 未信頼ワークスペースで network / 秘密ファイル / hooks / agent.env の境界が文書と一致する
5. `security-checklist.md` が実測と一致し、既知の制限が過大申告でない

## 6. リスクと前提

| リスク | 影響 | 緩和 |
|--------|------|------|
| E2E のフレーク | CI が信頼されない | ヘッドレス固定、タイムアウト余裕、再現手順の文書化 |
| `WorkspaceFs` 移行の広さ | 回帰 | 段階移行（書込系 → 読取系）、既存 PoC をゲートにする |
| 承認 UX の悪化 | ユーザーが無読で承認 | セッション許可ルールを S4 で同梱 |
| allowlist 移行 | 正当な env が消える | 端末同期 PATH は明示許可、移行ガイドを出す |

### 前提

- 対象リポジトリは `keijijin/codex-studio`（Codex Studio）
- 実行環境は macOS 開発機 + GitHub Actions（Linux）。Windows は hooks PowerShell 経路をユニットで担保
- 一次根拠は 2026-11-09 時点の再レビュー結果および未コミット修正後の再々レビュー結果
