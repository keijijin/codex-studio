## 1. 設計目標

1. ワークスペース外への読取・書込・削除を、ツール実装者の裁量に依存させない
2. 承認が必要な操作は、プレビュー専用経路以外で副作用を持てない
3. 信頼・秘密・ネットワークの境界を、設定と実行時ポリシーで一致させる
4. 起動不能クラスの欠陥を、CI の実アプリ経路で検出する

---

## 2. 現状アーキテクチャ上の弱点

```
Tool.execute()
  ├─ ctx.resolvePath()  … 呼ぶ場合のみ安全
  └─ fs.writeFile()     … 直接呼び可能 ← 抜け道

orchestrator
  └─ if (perm === 'ask' && tool.requiresApproval)  … AND 漏れ

preload (sandbox)
  └─ ビルド形式 (CJS/ESM) と webPreferences の整合が人間依存

workspace-trust
  └─ パス文字列のみ。内容変更で再確認なし
```

---

## 3. 目標アーキテクチャ

```
Tool.preview(ctx, args) → ApprovalMetadata（副作用なし）
        │
        ▼ 承認
Tool.apply(ctx, args) → WorkspaceFs.* のみ

WorkspaceFs
  ├─ resolve(path) / resolveUnlink(path)
  ├─ readText / writeText / appendText / unlink / mkdirp
  └─ roots: string[] をすべて試行

TrustService
  ├─ trustedRoots + contentHashes
  └─ ensureTrusted / reconfirmIfChanged / untrust

Preload API
  └─ typed methods only（汎用 invoke 禁止）
```

## 4. WorkspaceFs

### 4.1 責務

| メソッド | 挙動 |
|----------|------|
| `resolve(path)` | 全 root に対し symlink 安全解決。親ディレクトリの realpath 検証を含む |
| `resolveUnlink(path)` | 最終要素が symlink ならリンク自身の論理パスを返す（dangling 含む） |
| `readText` / `writeText` / `appendText` | resolve 後にのみ I/O |
| `unlink` | resolveUnlink 後にのみ I/O |
| `mkdirp` | 作成する各セグメントが root 内に留まることを保証 |

### 4.2 配置

- 実装: `packages/tools/src/workspace-fs.ts`（案）
- ToolContext に `fs: WorkspaceFs` を追加、または `resolvePath` を WorkspaceFs に置き換え
- `agent-core` の memory / team board は WorkspaceFs または `resolvePath` 必須 API のみ使用

### 4.3 ESLint

```js
// 概要（実装時に eslint.config へ）
'no-restricted-imports': ['error', {
  paths: [
    { name: 'fs', message: 'Use WorkspaceFs' },
    { name: 'fs/promises', message: 'Use WorkspaceFs' },
    { name: 'node:fs', message: 'Use WorkspaceFs' },
    { name: 'node:fs/promises', message: 'Use WorkspaceFs' },
  ],
}]
```

除外: `workspace-fs.ts` 本体、テスト、Electron main の非エージェント領域（設定ファイル等は別ルール）。

### 4.4 マルチルート

現行 `WorkspaceService.resolveWithinWorkspace` と同様、root を順に試し最初の成功を返す。Delete は `resolveUnlink` を同様に全 root で試行する。

## 5. Tool の preview / apply 分離

### 5.1 インターフェース（案）

```typescript
interface Tool {
  name: string
  description: string
  parameters: JSONSchema
  /** 副作用なし。承認 UI 用メタデータを返す */
  preview(ctx: ToolContext, args: Record<string, unknown>): Promise<ToolResult>
  /** 承認後のみ呼ばれる。WorkspaceFs 経由の副作用のみ許可 */
  apply(ctx: ToolContext, args: Record<string, unknown>): Promise<ToolResult>
}
```

読み取り専用ツールは `preview === apply` でもよいが、orchestrator は `perm === 'allow'` のときのみ `apply` を直接呼ぶ。

### 5.2 Orchestrator 判定

| permission | 動作 |
|------------|------|
| `deny` | 実行しない |
| `allow` | `apply` |
| `ask` | 必ず `preview` → ユーザー承認 → `apply` |

`requiresApproval` フラグは廃止するか、`ask` と同義のドキュメント専用にする。AND 条件は置かない。

### 5.3 MCP / メディア

外部副作用を持つツールは `preview` でネットワーク呼び出しを行わない（現行方針を型で固定）。

## 6. 信頼モデル

### 6.1 データ

```typescript
interface TrustedWorkspace {
  root: string              // realpath 正規化済み
  trustedAt: string         // ISO8601
  contentHashes: {
    hooksJson?: string
    agentEnv?: string
    // 必要に応じ skills / teams マニフェスト
  }
}
```

### 6.2 フロー

1. `ensureTrusted(root)` — 未登録ならダイアログ
2. 登録済みでもハッシュ不一致なら再確認ダイアログ
3. `untrust(root)` — UI および設定から呼び出し可能
4. 未信頼時: hooks 無効、agent.env 無効、ワークスペース Skills/Teams/Personas 無効、`network` を ask（設定が deny なら deny のまま。allow にはしない）

### 6.3 CLI / headless

既定は未信頼相当。`CODEX_TRUST_WORKSPACE=1` 明示時のみ overlay 適用（現行方針を仕様として固定し、CLI ヘルプに記載）。

## 7. 秘密ファイル・持ち出し

### 7.1 秘密パス glob（初期案）

| glob | Read 既定 |
|------|-----------|
| `**/.env` / `**/.env.*`（`.env.example` / `.sample` / `.template` 除く） | 信頼: **ask** / 未信頼: **deny** |
| `**/*.{pem,key}` | 同上 |
| `**/.codex/.agent-env.captured` | 常に **deny**（YOLO 不可） |
| `**/secrets.enc.json` | 常に **deny**（YOLO 不可） |

**U-1 確定（2026-11-09）**: 一般秘密は信頼時 ask・未信頼時 deny。常時 deny パスは YOLO でも拒否。`.env.example` 等のテンプレートは秘密扱いしない。

### 7.2 ネットワーク

| 状態 | network 権限 |
|------|----------------|
| 未信頼 | **ask**（設定が deny なら deny。allow には上げない） |
| 信頼済み | 設定プロファイルに従う |

**U-2 確定（2026-11-09）**: 未信頼の network 下限は ask。

プロンプトインジェクション対策の追加として、同一ターンで「大規模 Read → WebSearch」が連続した場合の監査イベントを検討する（S3 後半、※TODO）。

## 8. 環境変数

### 8.1 方針転換

除外リスト（denylist）から **許可リスト（allowlist）** へ移行する。**実装済み（2026-11-09）**: `filterEnvByAllowlist` / `AGENT_ENV_ALLOWLIST_*`。

### 8.2 レイヤ

| レイヤ | 許可の考え方 |
|--------|----------------|
| process 基底 | OS の現在の env（フィルタなし、または最小限の剥離） |
| `.codex/agent.env` | 厳密 allowlist（`KUBECONFIG` / `OC_*` / `AWS_*` 等。`PATH` 不可） |
| 端末同期 overlay | 同上 allowlist + `PATH` を明示許可。`HOME` / `ZDOTDIR` / loader 系は不許可 |
| Hooks 注入 | `CODEX_FILE` 等の固定キーのみ上書き |

未知キーは適用しない（`droppedKeys` にキー名のみ。値は出さない）。追加キーが必要な場合は allowlist 定数を拡張する。

## 9. Preload / IPC

### 9.1 Preload

- 出力形式: CJS 単一ファイル（`sandbox: true` 前提）をビルド設定で固定
- API: チャンネル名を引数に取る汎用 `invoke` を廃止し、`workspace.open` 等の typed メソッドのみ（**実装済み 2026-11-09**: `CodexApi` にドメイン別メソッド。Renderer から `window.codex.invoke` は不可）

### 9.2 Main

- `assertTrustedIpcSender` の完全一致を維持
- 未登録 IPC チャンネルはハンドラ未登録により失敗
